# 개요

데이터는 그냥 파일에 저장하면 되는데, 왜 굳이 DBMS라는 걸 따로 쓸까?  
이번 글에서는 DBMS가 등장하게 된 배경인 파일 중심 시스템의 한계를 먼저 보고,  
스키마와 인스턴스의 차이, 그리고 DBMS의 3단계 구조와 데이터 독립성에 대해 정리해보려 한다.

---

# 파일 중심 시스템의 한계

### 1. 파일 중심 시스템
- 응용 프로그램마다 자기 데이터 파일과 파일 접근 루틴을 따로 가지는 방식이다.
- 예를 들어 급여, 인사 기록 프로그램이 각자 파일을 하나씩 가진다.

이 방식에는 크게 두 가지 문제가 있다.

- **데이터 종속성(Data Dependency)**
  - 응용 프로그램과 데이터가 서로 강하게 묶여 있다.
  - 데이터의 구성이나 접근 방법을 바꾸면 프로그램도 같이 고쳐야 한다.
- **데이터 중복성(Data Redundancy)**
  - 같은 데이터가 여러 파일에 중복 저장된다.
  - 한 곳만 수정되면 데이터가 서로 달라지므로 일관성, 무결성, 보안성, 경제성을 보장하기 어렵다.

### 2. 파일 관리 시스템(FMS)
- File Management System
- 모든 데이터 파일에 대한 공동 접근 루틴을 제공한다.
- 하지만 프로그램마다 다른 데이터 구조를 지원하지 못해서, 종속성과 중복성 문제는 그대로 남는다.

### 3. DBMS의 등장
- DataBase Management System
- 응용 프로그램과 데이터 사이에서 **중재자** 역할을 하는 소프트웨어 시스템이다.
- 프로그램은 파일이 아니라 데이터베이스에 대해 연산을 요청한다.
- FMS가 해결하지 못한 종속성과 중복성 문제를 해결하기 위해 등장했다.

# 스키마와 인스턴스

### 1. 스키마(Schema)
- 데이터베이스의 구조에 대한 **설명**이다.
- 쉽게 말하면 컬럼 이름과 타입 같은 것이다.
- 데이터베이스를 만들 때 정의되고, 자주 바뀌지 않는다.
- intension이라고도 한다.

### 2. 인스턴스(Instance)
- 특정 시점에 데이터베이스에 **실제로 저장된 데이터**이다.
- 그 시점의 스냅샷이라고도 하며, state 또는 extension이라고도 한다.
- 데이터가 수정될 때마다 바뀐다.

```text
schema   : Name(String) | DOB(Date)  | Address(String) | Job(String) | Scale(Int)
instance : A.Jonhson    | 2/04/1960  | London          | Programmer  | 12
           B.Holiday    | 3/10/1947  | Leeds           | Analyst     | 14
```

나는 스키마를 클래스 정의, 인스턴스를 그 시점에 만들어진 객체들로 생각하니까 이해가 쉬웠다.

# DBMS의 3단계 구조와 데이터 독립성

DBMS는 데이터를 바라보는 관점을 3단계로 나누고, 각 단계마다 스키마를 둔다.

### 1. 외부 단계 (External Level)
- 사용자 관점. 각 사용자가 보는 **부분적인 뷰**를 정의한 것이 외부 스키마이다.
- 예를 들어 고객은 이름과 전화번호만 보고, 인사팀은 급여와 직급까지 본다.
- SQL의 View와 비슷하다.

### 2. 개념 단계 (Conceptual Level)
- 조직 전체 관점. 개념 스키마는 DB 전체의 논리적 설계이다.
- 엔터티, 속성, 관계 등을 표현하며 ER 다이어그램을 바탕으로 한다.

### 3. 내부 단계 (Internal Level)
- 물리적 저장 관점. 내부 스키마는 데이터가 실제로 어떻게 저장되는지 정의한다.
- 파일 구조, 인덱스, 해시 구조, 압축 등이 여기에 속한다.

외부 스키마의 값이 개념 스키마에서 바로 꺼낸 값이 아닐 수도 있다.  
예를 들어 재무팀이 보는 `Age`는 개념 스키마의 `DOB`로부터 계산되고, `Name`은 `Fname`과 `Sname`을 합친 것이다.  
이렇게 단계 사이를 이어주는 것을 사상(mapping)이라고 한다.
- 외부 ↔ 개념: 논리적 구조 사상
- 개념 ↔ 내부: 물리적 구조 사상

### 4. 데이터 독립성
3단계로 나누는 궁극적인 목적은 각 단계를 분리해서 한쪽의 변경이 다른 쪽에 영향을 주지 않게 하는 것이다.
- **논리적 데이터 독립성**
  - 응용 프로그램에 영향을 주지 않고 논리적 구조(개념 스키마)를 바꿀 수 있다.
- **물리적 데이터 독립성**
  - 응용 프로그램과 논리적 구조에 영향을 주지 않고 물리적 구조(내부 스키마)를 바꿀 수 있다.
  - 예를 들어 인덱스를 추가하거나 저장 방식을 바꿔도 프로그램은 그대로 둘 수 있다.

파일 중심 시스템의 데이터 종속성 문제를 정확히 뒤집은 것이 데이터 독립성이라고 보면 된다.

# 마치며

정리하면 DBMS는 파일 중심 시스템의 종속성과 중복성 문제를 해결하기 위해 등장했고,  
3단계 스키마 구조와 사상을 통해 데이터 독립성을 제공한다.
